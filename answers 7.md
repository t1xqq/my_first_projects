1. Какие HTML5-атрибуты используются для клиентской валидации и какую функциональность они предоставляют?
•	required - поле обязательно.
•	minlength / maxlength - минимальная/максимальная длина текста.
•	min / max - границы для чисел и дат.
•	pattern - регулярное выражение для проверки формата.
•	type - email, tel, url, number, date и т.д. - включают встроенные проверки.
•	step - шаг для числовых полей.
•	novalidate - отключает встроенную валидацию формы (используется, когда нужна своя JS-валидация).
2. В чем разница между novalidate атрибутом формы и отключением валидации через JavaScript?
•	novalidate - HTML-атрибут, полностью отключает встроенную браузерную валидацию. При этом checkValidity(), validity и CSS-псевдоклассы :valid/:invalid продолжают работать - их можно использовать в JS.
•	Отключение через JS (form.noValidate = true или input.removeAttribute('required')) - динамическое. Удобно, когда нужно менять правила в зависимости от условий.
В работе используется novalidate, чтобы самостоятельно управлять показом ошибок и не полагаться на браузерные tooltip'ы.
3. Как правильно связать <label> с полем ввода и почему это важно для доступности?
Два способа:
•	for="id" у <label> и id="..." у input (основной способ).
•	Обернуть input внутрь <label> (для чекбоксов/радио).
Важно, потому что:
•	Клик по label фокусирует поле - удобно для тач-устройств.
•	Скринридеры читают label как описание поля.
•	Улучшает SEO и общую доступность (WCAG).

6. Какие события JavaScript используются для реализации валидации в реальном времени и почему?
•	blur - при потере фокуса (когда пользователь ушёл с поля). Удобно: не мешает вводу.
•	input - при каждом изменении. Используется для очистки ошибки и для live-счётчиков (textarea).
•	submit - при отправке формы, финальная проверка.
•	change - для select, checkbox, radio.
В работе: blur → валидация, input → очистка ошибки. Это классический баланс UX: не ругаем пользователя, пока он печатает, но проверяем, когда он закончил.
7. Как обеспечить доступность сообщений об ошибках для пользователей скринридеров?
•	Связывать поле с сообщением через aria-describedby="fieldError".
•	Добавлять aria-invalid="true" при ошибке.
•	Использовать role="alert" или aria-live="polite" на контейнере ошибки, чтобы скринридер озвучивал изменение.
•	Не полагаться только на цвет - добавлять текст и/или иконку.
•	Помечать обязательные поля через required (скринридер сам скажет «обязательное»).

8. В чем преимущества использования fieldset и legend для группировки полей формы?
•	Семантика: логически связанные поля объединяются (например, «Личная информация», «Безопасность»).
•	Доступность: скринридеры озвучивают legend перед каждым полем группы - пользователь понимает контекст.
•	Стилизация: легко оформить группу рамкой, отступами.
•	Навигация: улучшает восприятие длинных форм.
В работе три fieldset - «Личная информация», «Безопасность», «Дополнительная информация».

9. Как реализовать кастомную валидацию для сложных случаев (например, подтверждение пароля)?
Через JS: слушаем input/blur на обоих полях и сравниваем значения
Дополнительно можно
•	Использовать setCustomValidity('...') для интеграции с браузерной валидацией.
•	Проверять сложные условия (например, пароль не должен содержать имя).
•	Подключать input на обоих полях, чтобы ошибка исчезала сразу при исправлении.
